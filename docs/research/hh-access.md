# Исследование доступа к hh

Дата: 29 октября 2026. Исследование предварительное. После настройки VPN доступ к аккаунту восстановлен; поиск через MCP по-прежнему завершается 403 при обращении к чатам. Изменений в hh и отправок не выполнялось.

## Уточнение и поиск вариантов

- Семён подтвердил приоритет адресной выдачи вакансий по каждому резюме. Если её получить не удастся, предпочтителен единый общий поиск с последующей оценкой всех трёх резюме; этот запасной вариант пока не принят как замена исследованию.
- Семён выбрал считать отклик отправленным при успешном ответе hh, если прочитать текст письма невозможно, и продолжить исследование возможностей повторной проверки. Таймаут или неоднозначный ответ остаются неопределёнными.
- В старой документации API встречается `GET /resumes/{resume_id}/similar_vacancies` ([историческая копия документации](https://github.com/vasili8m/hh-api/blob/master/docs/resumes.md)). Это перспективная зацепка, но действующую поддержку метода и его доступность для текущей авторизации ещё предстоит подтвердить; старую копию не считаем актуальной спецификацией.
- 29 октября MCP успешно прочитал три резюме с заголовками Senior Python Backend разработчик, Senior AI Engineer / Python-разработчик, Ведущий Python-разработчик / Tech Lead. Их окончательное соответствие рабочим профилям и видимость отдельно не подтверждены.
- UI hh через инструмент управления браузером в этой итерации не удалось открыть: helper завершился с `helper_sandbox_lock_failed` и кодом доступа 5. Это ошибка локального средства управления, а не ответ hh.

## Повторная проверка после настройки VPN, 29 октября 2026

- `whoami` и `resumes` успешно прочитали аккаунт соискателя и четыре резюме. Прежняя SSL-ошибка для этих методов устранена; соответствие трём рабочим профилям ещё нужно проверить.
- `suitable_vacancies` вернул шесть показанных вакансий из 447 заявленных. Привязка к конкретному резюме, фильтр сегодняшнего дня и доступность всех страниц остаются неподтверждёнными.
- `search` по Python, за один день и одну страницу снова вернул HTTP 403 на `chatik.hh.ru/chatik/api/chats`. Это ответ сервера, а не прежняя ошибка TLS; причину 403 установить не удалось. Код обёртки делает запрос истории после поиска, поэтому результат поиска отдельно не подтверждён.
- После 403 дальнейшие запросы hh в этом обходе остановлены. Изменений резюме и откликов не было.

## Источники и код

- [Официальные ошибки hh](https://github.com/hhru/api/blob/master/docs/errors.md) — `test_required`, `already_applied`, `limit_exceeded`.
- [Документация соискателя](https://github.com/hhru/api/blob/master/docs/vacancies_for_applicant.md): `suitable_resumes_url` относится к поиску резюме для найденной вакансии, не к подбору вакансий для заданного резюме.
- [Официальный поиск вакансий](https://github.com/hhru/api/blob/master/docs/vacancies.md) ссылается на OpenAPI; применимость к аккаунту и пагинация не проверены.
- Изучена локальная интеграция antalez/hh-cv-mcp, commit `a0b72fb`: `server.py`, `hh_client.py`, `LICENSE.md`. Лицензия PolyForm Noncommercial 1.0.0; код не копировался и не запускался. `server_limited.py` только регистрирует выбранные методы и импортирует код клиента.

## Следующий шаг

Сопоставить три резюме и проверить адресные рекомендации, фильтр дня и страницы. Отдельно выяснить причину 403 чатов и проверить поиск без зависимости от чатов. До результата нельзя утверждать, что подходящий источник найден или история полная. Не отправлять отклики и не менять резюме в ходе исследования.

## Прямой поиск по резюме — 29 октября 2026

Из кода [iraguzov/hh-mcp-server](https://github.com/iraguzov/hh-mcp-server) получена идея проверить страницу поиска с параметрами `resume=<ID>`, `from=resumelist`, `page`, `items_on_page`, `search_period=1` и сортировкой `publication_time`. Выполнены собственные read-only GET-запросы к hh с существующей локальной авторизацией; исходный код стороннего проекта не запускался. Сначала был сетевой сбой, после чего повторный запрос сработал.

- Три предполагаемых рабочих резюме по отдельности вернули HTTP 200 и соответственно 45, 61 и 71 результат на момент проверки; по 20 вакансий на первой странице.
- Для первого резюме вторая страница вернула ещё 20 вакансий с другими первыми ID; это подтверждает доступность двух страниц, но не полноту всех страниц или отсутствие пересечений во всей выдаче.
- В ответе `proxiedSearchFormParams` отражались переданные ID резюме и `search_period`. Примеры первых дат имели часовой пояс `+03:00`. Это подтверждает передачу параметра и получение отличающихся выдач, но не доказывает точную идентичность выдаче из UI и семантику алгоритма hh.
- `search_period=1` не доказан как календарный московский день. Нужно проверить все страницы, поля дат, фильтрацию текущего дня и совпадение с переходом из интерфейса; отдельно — поведение при обновлениях и пустом результате. Поиск пока не считается полностью принятым для автоматизации.
- Получение этих страниц не требует списка чатов в проверенном запросе. Проверка не выясняет причину 403 чатов, доступ к истории и наличие форм для откликов.
