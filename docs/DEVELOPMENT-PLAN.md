# План разработки

Дата: 29 октября 2026. Статус: план подготовлен, реализация не начата.

Цель первой версии: один личный сервис, который получает свежие вакансии доступным согласованным способом, оценивает три профиля, сохраняет объяснимые решения и историю, формирует Telegram-отчёты и после отдельных испытаний поддерживает управляемую отправку.

Бизнес-правила — в [решениях от 28 октября](05-automation-decisions-2026-10-28.md), с учётом более свежих решений Семёна в [открытых вопросах](OPEN-QUESTIONS.md) и [архитектуре](ARCHITECTURE.md). Старые пункты базового проекта о фильтрах, одном резюме и одностороннем Telegram не заменяют более свежие решения.

## Порядок и зависимости

P0 — главная неопределённость. От его результата зависит конкретный адаптер hh. До завершения исследования можно сделать изолированный каркас P1 и тестовые интерфейсы; схему предметных данных, конкретный поисковый конвейер и отправку заранее не реализуем. Не выдаём наличие каркаса за готовность интеграции.

## P0. Проверить источники и договориться о данных

1. Выполнить [исследование 06](06-resume-vacancy-discovery.md): соответствие трёх профилей реальным ID, видимость, адресный поиск или согласованная альтернатива, московский день, сортировка, пагинация, повторный сбор и полнота. Не менять резюме и не отправлять отклики.
2. Сравнить доступный официальный интерфейс с существующей интеграцией; установить причину зависимости поиска от чатов и ограниченного текстового вывода. По решению Q-11 разрешено искать и изучать инструменты hh и опыт их использования, включая относящиеся к ним локальные материалы и внешние источники. Не переносить стороннюю реализацию вслепую. Резюме и сведения об опыте получать из самого hh.
3. Проверить историю откликов и архивы, статусы, сообщения, непрочитанность, побочные эффекты чтения, распознавание форм, возможности подтверждения отправки и проверки письма. Разделить возможности чтения и записи; успешность одной не доказывает другую.
4. Зафиксировать доступные ограничения, частоту запросов и правила интерфейса. Не проверять порог блокировки экспериментом.
5. Пройти Q-01, Q-02, Q-03, Q-05, Q-06, Q-07 и Q-11 в части, необходимой следующему этапу. Согласовать состав данных для ручного анализа до проектирования схемы, в том числе состав доступной переписки.

**Артефакт:** `docs/research/hh-access.md` с таблицей способ → возможность → свидетельство/время → полнота → ошибки → решение. В Git только обезличенные результаты; реальные снимки и ID — в локальных данных. Артефакт создаётся по результатам работы, пустой отчёт с вымышленными выводами не нужен.

**Приёмка:** выбран и согласован источник либо зафиксирован блокер с конкретной проверяемой альтернативой. Нельзя закрыть P0 фразой «есть 822 вакансии» без доступа к страницам. Неполнота чатов может ограничить мониторинг, но не обязана блокировать независимый доступный поиск; ограничения явно согласуются.

## P1. Каркас приложения и изолированные проверки

1. Создать pyproject, lock-файл, изолированную среду Python 3.14, пакет `src/`, CLI и пример настроек без личных данных.
2. Добавить проверку конфигурации, часовую зону, структурированные ошибки и журналирование с маскированием секретов. Неверная конфигурация запрещает сетевую работу.
3. Создать минимальные границы адаптеров hh, Telegram, часов и хранилища; тестовые реализации. Не строить универсальный фреймворк плагинов.
4. Реализовать минимальное локальное состояние управления, межпроцессный lock и режим dry-run по умолчанию. Это техническое состояние; предметная схема ждёт P0/P2.
5. Настроить pytest и Ruff. Добавить CI GitHub Actions с проверками на Windows и Linux, без аккаунтов и секретов. Команды установки/проверок записать в README после того, как они реально заработают.

**Приёмка:** приложение запускается с фикстурами, отсутствующие настройки объясняются, второй экземпляр завершается без сетевых обращений; `/on` не способен сменить режим на automatic. Никакого доступа к hh по умолчанию.

## P2. Хранилище и восстановление

1. По согласованному составу данных спроектировать схему и модель состояний. Сохранить связи вакансий/снимков, профилей, оценок, правил, писем, попыток, событий, запусков и уведомлений.
2. Реализовать нумерованные миграции, транзакции, уникальность отправки на vacancy ID, импорт ручной истории с отметкой полноты, сохранение незавершённых операций.
3. Реализовать версии и снимки, чтобы последующая правка live-резюме, шаблона или вакансии не переписывала прошлое решение.
4. Создавать уведомления транзакционно вместе с изменением состояния; реализовать повторную доставку независимо от hh.
5. Историю хранить без автоматического удаления; очистка — по указанию Семёна. Резервные копии не создавать.

**Приёмка:** повторный импорт не создаёт дубли, обрыв записи не оставляет полурешение, после рестарта доступны неопределённые попытки и недоставленные отчёты.

## P3. Рейтинг трёх профилей и письма

1. Подготовить три подтверждённых профиля фактов/синонимов с реальными ID и версиями. Содержание не выдумывать; персональные файлы вне Git.
2. Реализовать отдельно зарплатное отсечение, смысловой рейтинг и выбор резюме. Наличие слова не равно подтверждённому навыку; отрицания и неизвестные значения учитываются явно.
3. Реализовать состав оценки, три итоговых балла и читаемые причины. Если все оценки ниже порога — отчётный элемент один раз; обязательный навык сам по себе не превращается в ручную блокировку.
4. Выбирать первый подходящий шаблон по заданному порядку; проверять подстановки и предусмотреть универсальный запасной шаблон. Неполный пул не должен приводить к отправке без письма.
5. Собрать и вручную разметить разнообразную выборку; отделить настройку от проверки. Сохранить ошибки допуска, полноту, качество выбора профиля и спорные случаи; согласовать пороги и критерии Q-05.

**Приёмка:** воспроизводимые оценки с объяснениями; покрыты RUB 199999/200000, отсутствие верхней границы, другая валюта, gross/net, отрицания и профильные пересечения. При изменении шаблонов прошлый текст письма остаётся прежним. Порог 50 не объявляется проверенным до разметки.

## P4. Сбор и полный dry-run

1. Реализовать выбранный в P0 адаптер без лишних зависимостей и скрытых повторов. Все реальные запросы проходят единый шлюз доступа.
2. После результатов исследования конкретизировать поиск, курсоры по источникам/профилям, перекрытие, условия успешного полного обхода и поведение при частичном результате. Проверять реальную дату публикации в пределах сегодняшнего дня Москвы.
3. Сохранять полученные снимки, оценки, дубли, зарплатные исключения, ручные формы и случаи ниже порога. Старые очереди перепроверять по дате, режиму и версии данных; не отправлять вчерашнее автоматически.
4. Сверять доступную историю и отмечать неполноту; подозрения на републикацию с новым ID выводить для ручной проверки.
5. Сначала прогнать фикстуры, затем небольшой живой read-only обход. Реальную отправку технически исключить в dry-run.

**Приёмка:** время и охват сбора видны в отчёте, перелистывание не теряет страницы молча, частичный обход не продвигает успешный курсор; повтор не создаёт повторных решений/уведомлений без причины. 403/429 останавливает последующие hh-запросы.

## P5. Telegram, расписание и мониторинг

1. Подключить отдельного бота владельца; реализовать `/on`, `/off`, `/status`, проверку отправителя/чата и дедупликацию updates. Применить согласованную политику старых команд.
2. Реализовать один отчёт за обход с целыми ссылками и частями, отдельные критические уведомления, сохранённую очередь и Retry-After. Тестировать длинные названия, Unicode и недоступность Telegram.
3. Подключить пять московских слотов, защиту от перекрытия, сон/пробуждение Windows, рестарт и отсутствие лавины пропущенных запусков.
4. По подтверждённым возможностям P0 реализовать read-only мониторинг с частотой Q-08: только новые изменения, исходные статусы и честная отметка неполноты. `/off` останавливает и его.
5. Описать запуск процесса и перезапуск в выбранной среде Q-04. `/status` показывает режим, разрешение hh и причину паузы, текущий/последний обход, ближайший слот, очередь, счётчики лимитов и состояние источников без сетевого запроса hh.

**Приёмка:** команда `/off` обрабатывается во время ожидания сети, результат уже начатого запроса сохраняется, новых запросов нет. Посторонний пользователь не меняет состояние. Перезапуск не теряет выключенное состояние и очередь; Telegram-сбой не повторяет отклик.

## P6. Механизм отправки на имитациях

1. Согласовать модель статусов и проверки результата с доступными свидетельствами P0. Реализовать атомарные проверки дублей, режима, формы, письма, подтверждения пилота, истории и лимитов перед сохранением намерения.
2. Реализовать единственную попытку отправки без автоматического сетевого повтора, проверку письма при доступности, учёт UTF-8 и фактического письма. При успешном ответе hh, если письмо невозможно прочитать, считать отклик отправленным и отметить отсутствие проверки текста. `test_required` → ручная очередь; `already_applied` → сверка истории, ограничения → пауза.
3. При падении в любой точке после намерения сохранять необходимость сверки. Неизвестный исход не освобождает резерв лимита и не допускает новую отправку.
4. Реализовать локальную ручную очередь и предпросмотр подтверждаемой вакансии, резюме и письма для пилота. Сам факт попадания в очередь ничего не отправляет.

**Приёмка:** тестовые сценарии покрывают падение до запроса и после него, таймаут, повтор запуска, две конкурирующие попытки, неполную историю, смену резюме, форму, повреждённое письмо и лимиты суток/24 часов. Все проверки выполняются на имитациях без реальных откликов.

## P7. Управляемый пилот

1. Предъявить результаты dry-run и локальных проверок, открытые ограничения и конкретные вакансии/письма для подтверждения.
2. По отдельному поручению выполнить выбранные одиночные отправки. Не более 5 за обход и 15 за календарные сутки; отдельно применить предел скользящих 24 часов. Считать попытки и неопределённые исходы, а не только успешные отклики.
3. Сверить каждый исход повторным чтением, доставку отчёта и сохранённые снимки. При неопределённости остановиться для разбора соответствующего случая, не повторять отправку.
4. Сравнить ручные решения и рекомендации, уточнить правила и завершить вопросы, блокирующие автоматический режим.

**Приёмка:** согласованный объём пилота выполнен, все попытки имеют свидетельства или явно неразрешённый статус, повторов нет, ограничения и решения задокументированы. Наличие неразрешённых критических исходов блокирует автоматический режим.

## P8. Автоматический режим и эксплуатация

1. Зафиксировать проверенные профили, письма, пороги, доступные рабочие лимиты и условия остановки; не считать испытательные лимиты доказанно безопасными рабочими.
2. Отдельным решением включить automatic; проверить, что `/on` после сбоя возобновляет только разрешённый режим и не обходит лимиты.
3. После завершения локальной разработки развернуть сервис на VPS по решению Q-04; доступ Семён предоставит на этапе деплоя. Уточнить ОС и автозапуск, перенести данные и настройки с остановленным локальным экземпляром, чтобы два процесса не работали с одним аккаунтом. Сначала проверить на VPS dry-run, затем восстановить отдельно разрешённый режим. Довести инструкции установки, обновления, диагностики, обновления авторизации, разбора неопределённых попыток.
4. Выполнить контрольный рестарт и восстановление в тестовой папке; проверить локальные права на данные, маскирование секретов и отсутствие личных файлов в Git.

**Готово:** сервис работает на выбранном хосте, полная история собственных действий восстанавливается, неполнота внешней истории видна, автоматические повторы откликов исключены, команды управления и отчёты проверены. Дополнительные функции не нужны для завершения первой версии.

## Проверки и порядок работы

Каждый этап завершается небольшим коммитом с результатом и относящимися к нему проверками. Поведение, связанное с данными, дублями, управлением и сетью, проверяем содержательными тестами; документационные правки не требуют искусственных unit-тестов. CI работает на синтетических данных и не выполняет живые hh/Telegram-операции.

Матрица обязательной проверки перед пилотом: зарплатные границы; три профиля; версии писем; пагинация и часовой пояс; дубли и републикации; неполная история; формы; таймаут после отправки; падение/рестарт; конкуренция; `/off` во время запроса; команды Telegram за время простоя; независимая доставка. Контрольный живой read-only прогон не заменяет тесты падений.

Календарную оценку даём после P0: стоимость доступа к hh пока неизвестна и может превысить стоимость самого сервиса. Остальные этапы намеренно малы и дают проверяемый результат, без отдельного проекта инфраструктуры.

## Уточнение по пилоту и письмам

Выбираем первый подходящий шаблон. После проверки нескольких десятков вакансий запускаем ограниченный автоматический пилот без согласования каждой вакансии, с ранее установленными лимитами. Это решение заменяет противоречащие пункты плана о ротации писем и подтверждении каждой вакансии.
